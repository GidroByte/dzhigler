# dzhigler

USB-адаптер на RP2040-Zero 2МБ. С одной стороны — хост-порт для обычной
USB-клавиатуры или мыши, с другой — композитное HID-устройство
(клавиатура + мышь + CDC-консоль) для ПК.

Адаптер включается в разрыв между мышью и ПК и передаёт ввод без изменений: мышь видит хост-порт, ПК — ту же мышь, что и при прямом подключении. Пока через адаптер не идёт ввод дольше заданного времени, он сам генерирует движения мыши, чтобы ПК не уходил в сон, не гасил экран и не считал сессию простаивающей; как только ввод возобновляется, генерация прекращается. От готовых USB-джиглеров это отличает то, что в разрыв включается рабочая мышь, а генерация привязана к отсутствию ввода, а не к таймеру: пока вы работаете, адаптер курсор не трогает. Параметры задаются через консоль, хранятся во flash и переживают перепрошивку.

Проект любительский. Отладочная плата стоит столько же или дешевле готового джиглера, но её надо собрать, спаять и посадить в корпус. Выигрыш не в цене, а в том, что поведение задаётся пользователем и джиглер не мешает работе.


## Как это работает

| Роль | Ядро | Шина |
| --- | --- | --- |
| USB HOST | core1 | PIO USB (GP0 = D+, GP1 = D−) |
| USB DEVICE | core0 | нативный USB (разъём платы) |

Ядро 1 перечисляет подключённое устройство, разбирает его HID report
descriptor и определяет роль интерфейса: мышь, клавиатура или
композит с несколькими Report ID. Отчёты складываются в очередь и
передаются на ядро 0.

Ядро 0 одновременно поднимает нативный USB в режиме устройства
(HID-мышь, HID-клавиатура, CDC), пробрасывает отчёты на ПК,
обслуживает CDC-консоль настроек и, когда пользователь долго
не активен, генерирует синтетическое движение мыши.

Со стороны ПК адаптер виден как одно композитное устройство из
четырёх интерфейсов:

| Интерфейс | Назначение |
| --- | --- |
| HID Keyboard | трансляция нажатий с хост-порта |
| HID Mouse | трансляция перемещения и кнопок, синтетический jiggle |
| CDC (2 интерфейса) | консоль настроек и диагностический вывод |

VID/PID — `0xCafe`/`0x4001` (демонстрационные идентификаторы TinyUSB,
не зарегистрированные в USB-IF). Найти устройство на шине можно
по ним (`lsusb`).

### Jiggle

Джигл — плавный сдвиг курсора на небольшое случайное расстояние,
пауза и возврат в исходную точку. Запускается, когда выполнены
оба условия:

- прошло не менее `idle_before_ms` с последнего зафиксированного
  действия пользователя;
- прошло не менее `jiggle_gap_*` с окончания предыдущего джигла.

Первое движение после включения — не раньше, чем через 1 с
с момента старта.

Активностью считаются:

- движение мыши с суммой $|x| + |y| \ge$ `act_min_px`;
- прокрутка колеса;
- изменение состояния кнопок мыши;
- изменение модификаторов или набора клавиш на клавиатуре.

Если пользователь подействовал во время джигла, тот прерывается
и возврат курсора выполняется ускоренно (`abort_return_ms`).

Пока джигл идёт, отчёты реальной мыши на ПК не отправляются —
курсор не дёргается от двух источников одновременно. Они
накапливаются в очереди и уходят после завершения джигла.

## Зависимости

CMake ничего не скачивает сам: пути к зависимостям передаются
переменными.

| Переменная | Значение |
| --- | --- |
| `PICO_SDK_PATH` | путь к pico-sdk, обязательно |
| `PICO_PIO_USB_PATH` | путь к Pico-PIO-USB, обязательно |
| `PICO_TINYUSB_PATH` | по умолчанию `${PICO_SDK_PATH}/lib/tinyusb` |
| `PICO_BOARD` | по умолчанию `pico` |

TinyUSB отдельно подключать не нужно — он берётся из pico-sdk.
Но `lib/tinyusb` внутри pico-sdk является вложенным сабмодулем:
клонирование без `--recursive` оставит каталог пустым.

    git clone --recursive https://github.com/raspberrypi/pico-sdk.git
    # если уже клонирован без сабмодулей:
    cd pico-sdk && git submodule update --init --recursive

Pico-PIO-USB и версия TinyUSB из pico-sdk должны поддерживать
host через PIO. Если `hcd_pio_usb.c` в TinyUSB не найден, сборка
останавливается с указанием полного пути, по которому его искали.

## Сборка

    git clone https://github.com/<user>/dzhigler.git
    cd dzhigler

    cmake -B build -S . -G Ninja \
        -DPICO_SDK_PATH=/path/to/pico-sdk \
        -DPICO_PIO_USB_PATH=/path/to/Pico-PIO-USB

    cmake --build build -j"$(nproc)"

Результат — `build/dzhigler.uf2`.

Каталог сборки привязан к генератору: CMake запоминает
выбранный в `build/CMakeCache.txt` и отказывается
использовать тот же каталог с другим генератором. Если `build/`
уже сконфигурирован без `-G Ninja` (например, `Unix Makefiles`),
конфигурация остановится с ошибкой `generator ... does not match
the generator used previously` — удалите каталог (`rm -rf build`)
и повторите.

Пути можно задать переменными окружения `PICO_SDK_PATH` и
`PICO_PIO_USB_PATH` вместо `-D`. Тип сборки по умолчанию —
`Release`; поменять можно через `-DCMAKE_BUILD_TYPE=Debug`.

Прошивка одна на все случаи: отдельной «отладочной» сборки нет,
диагностический вывод включается на ходу из консоли (см. ниже).

### Проверка размера прошивки

Последний сектор флеша (4096 байт) зарезервирован под хранение
настроек. Линкер об этом секторе ничего не знает, поэтому после
сборки автоматически запускается проверка
(`cmake/check_flash_size.cmake`): она читает LOAD-секции готового
ELF, вычисляет самый дальний занятый адрес и останавливает сборку
с ошибкой, если образ доходит до зарезервированного сектора.

Проверка запускается при обычной сборке всего проекта
(`cmake --build build`). Если собирать только цель
(`cmake --build build --target dzhigler`), она не выполнится.

Проверку можно намеренно провалить, указав заведомо маленький размер
флеша. Бюджет вычисляется из него вычитанием последнего сектора, так
что в выводе будет 69632 байта, а не 73728:

    cmake -B build-fail -S . -G Ninja \
        -DPICO_SDK_PATH=... -DPICO_PIO_USB_PATH=... \
        -DDZHIGLER_FLASH_TOTAL_BYTES=73728   # размер флеша, не бюджет
    cmake --build build-fail -j"$(nproc)"   # ошибка: 75664 B > 69632 B

Артефакт из такой сборки прошивать нельзя: адрес сектора настроек
вычисляется из того же значения, и в тестовой конфигурации он
указывает внутрь кода. Каталог с тестовой сборкой — только
одноразовый, после проверки его нужно удалить.

## Прошивка

Способ 1, BOOTSEL:

1. Зажать BOOTSEL.
2. Подключить USB.
3. Отпустить BOOTSEL — появится накопитель `RPI-RP2`.
4. Скопировать `dzhigler.uf2` на этот накопитель.

Способ 2, picotool:

    picotool load -f build/dzhigler.uf2

После прошивки USB следует передёрнуть физически: хост кэширует
дескрипторы, поэтому программное переподключение порта оставляет
старое устройство на шине.

Настройки во flash при перепрошивке сохраняются: новый образ
не занимает последний сектор, и загрузчик его не пишет.

## Подключение устройства

Хост-порт разведён на GP0 (D+) и GP1 (D−), конкретной распайки
разъёма код не предполагает — нужен переходник под нужный тип
разъёма, например USB-A или USB-C.

Порты GP0 и GP1 заняты, поэтому stdio UART недоступен.

Поддерживаются клавиатуры, мыши и композитные донглы, а также
устройства за USB-хабом.

## Консоль

Консоль поднимается вместе с устройством как CDC. Подключение:

    tio /dev/ttyACM0                 # Linux
    tio /dev/cu.usbmodem*            # macOS

Скорость значения не имеет: это виртуальный COM-порт, а не UART.

Через ~200 мс после открытия порта автоматически печатается справка
(`help`) — это нужно, чтобы не потерять вывод, пока хост открывает
CDC.

| Команда | Действие |
| --- | --- |
| `help` | список команд и параметров |
| `get` | текущие значения параметров |
| `set <name> <value>` | изменить параметр в памяти |
| `save` | записать текущие значения во flash |
| `load` | перечитать значения из flash |
| `defaults` | сбросить к значениям по умолчанию (в памяти) |
| `verbose on\|off` | фоновый диагностический вывод |

`set` меняет только рабочую копию в памяти — она действует
до перезагрузки и теряется, если не выполнить `save`. `load`
и `defaults` тоже не сохраняют результат во flash.

Поддерживается эхо ввода и backspace. Истории команд нет,
управляющие последовательности (стрелки и т. п.) не обрабатываются
и вставляются в строку как есть.

`verbose` не сохраняется: после перезагрузки вывод снова выключен.

## Параметры

Все времена в миллисекундах, радиусы в пикселях.

| Параметр | Диапазон | По умолчанию | Смысл |
| --- | --- | --- | --- |
| `idle_before_ms` | 500…3600000 | 30000 | простой, после которого разрешён джигл |
| `act_min_px` | 1…127 | 2 | порог $\lvert x\rvert+\lvert y\rvert$, с которого движение считается активностью |
| `abort_return_ms` | 10…10000 | 80 | длительность возврата при прерванном джигле |
| `jiggle_radius_min` | 1…127 | 2 | минимальный радиус сдвига |
| `jiggle_radius_max` | 1…127 | 5 | максимальный радиус сдвига |
| `jiggle_dur_min_ms` | 10…60000 | 120 | минимальная длительность ухода |
| `jiggle_dur_max_ms` | 10…60000 | 280 | максимальная длительность ухода |
| `jiggle_hold_min_ms` | 0…60000 | 120 | минимальная пауза в дальней точке |
| `jiggle_hold_max_ms` | 0…60000 | 400 | максимальная пауза в дальней точке |
| `jiggle_gap_min_ms` | 1000…3600000 | 30000 | минимальный интервал между джиглами |
| `jiggle_gap_max_ms` | 1000…3600000 | 60000 | максимальный интервал между джиглами |

Радиус, длительность, пауза и интервал выбираются случайно
в диапазоне между соответствующими `min` и `max` при каждом джигле.

`save` проверяет пары и отказывается писать, если `min` больше
`max` у радиуса, длительности, паузы или интервала.

## Хранение настроек

Настройки лежат в последнем секторе флеша: смещение `0x1FF000`
(адрес через XIP `0x101FF000`), 4096 байт. Структура — 56 байт:
сигнатура, версия и одиннадцать параметров по 4 байта, плюс CRC32.

Валидность записи проверяется по сигнатуре `0x445A4831` («DZH1»),
версии структуры и CRC32. При первом включении, пустом чипе,
повреждённой или несовпадающей по версии записи применяются
значения по умолчанию — автоматически, без дополнительных действий.

Если чип имеет другой размер флеша (не 2 МиБ), значение
`DZHIGLER_FLASH_TOTAL_BYTES` при сборке нужно задать соответственно
— от него вычисляется и адрес сектора настроек, и бюджет для
проверки размера.

## Диагностика

`verbose on` включает фоновый вывод в CDC. Вывод событийный,
не на каждый HID-отчёт.

| Метка | Что показывает |
| --- | --- |
| `[USB]` | подключение/отключение устройства со стороны ПК |
| `[KBD]` | готовность клавиатурного интерфейса на стороне ПК |
| `[MAP]` | разобранная карта Report ID для активного слота хоста |
| `[HB]` | heartbeat, раз в секунду: счётчики и состояние |

Расшифровка `[HB]`:

    [HB] m_if=2 k_if=3 q=0 ovf=0 | rep m=1234 k=56 bad=0 |
         mount m=1 k=1 oth=0 um=0 | ep m=1 k=1 lb=00 lsb=00 |
         jig=3 ab=1 busy=0 idle=45231ms

| Поле | Смысл |
| --- | --- |
| `m_if`, `k_if` | слот мыши и клавиатуры на хост-стороне, 255 — нет |
| `q`, `ovf` | длина очереди мыши и счётчик слияния при переполнении |
| `rep m`, `rep k`, `rep bad` | принято отчётов: мышь, клавиатура, нераспознанные |
| `mount m`, `mount k`, `mount oth`, `um` | монтирования мыши, клавиатуры, прочих, отключения |
| `ep m`, `ep k` | готовность HID-интерфейсов на стороне ПК |
| `lb`, `lsb` | последние принятые / отправленные кнопки мыши |
| `jig`, `ab` | всего джиглов и из них прерванных активностью |
| `busy`, `idle` | считается ли устройство занятым, и сколько простоя |

По этим полям проверяется основное поведение: `jig` растёт со
временем, `ab` — при движении мыши во время джигла; `busy`
переходит в 0 после `idle_before_ms` простоя и держится в 1,
пока идёт печать или движение.

## Надёжность

Включён аппаратный watchdog с таймаутом 3000 мс. Он подкармливается
на каждой итерации основного цикла и внутри блокирующих ожиданий
(движение синтетической мыши, вывод в CDC). Если core0 зависает
дольше трёх секунд — устройство перезагружается само.

Watchdog подкармливается только с core0. Зависание core1 само
по себе перезагрузку не вызовет: перестанет обновляться проброс
реального устройства, но консоль и jiggle продолжат работать.

При записи настроек во flash core1 останавливается через
multicore lockout — иначе второе ядро может читать код из флеша
во время стирания, что для RP2040 фатально. Поэтому `save`
блокирует оба ядра примерно на 50–100 мс.

## Ограничения

- Мышь: относительные координаты. Абсолютные устройства
  (планшеты, тачскрины) не поддерживаются. Кнопок — до пяти,
  остальные ПК не увидит.
- Клавиатура: 8-байтовый boot-отчёт. Для ПК адаптер всегда
  выглядит как boot-клавиатура, поэтому NKRO не транслируется.
  Если физическая клавиатура работает в report protocol и шлёт
  более длинные отчёты, используются только первые 8 байт —
  коды за их пределами будут неверными.
- Композитные устройства с несколькими Report ID в одном
  интерфейсе поддерживаются, но только если после отделения Report ID
  отчёт укладывается в ожидаемый размер: 3–4 байта для мыши,
  8 байт для клавиатуры.
- Переход в Boot Protocol (`Set_Protocol`) не выполняется никогда —
  сознательно: он ломает композитные донглы и урезает
  NKRO-клавиатуры. Роль интерфейса определяется только разбором
  report descriptor.
- Одновременно транслируются одна мышь и одна клавиатура. Если
  подключено несколько устройств одного класса, работает последнее
  смонтированное; отключение любого очищает слот, даже если
  другое устройство того же класса осталось подключённым.
- Движение мыши во время джигла накапливается в очереди на
  16 событий и при переполнении сливается с ограничением
  ±127 пикселей на ось. Быстрое движение в момент джигла может
  дойти до ПК не полностью.
- Индикаторы Caps/Num/Scroll Lock на физической клавиатуре
  не отражают состояние на ПК: LED-состояние, приходящее с ПК,
  не пересылается обратно в хост-порт.
- stdio недоступен: GP0 и GP1 заняты хост-портом, а USB-stdio
  поднял бы второе CDC-устройство и сломал композитный дескриптор.
  Весь вывод идёт через собственный CDC.
